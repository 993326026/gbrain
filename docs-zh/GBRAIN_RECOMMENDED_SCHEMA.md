# Brain: LLM 维护的知识库

这是一份系统提示词，供任何想要构建和维护个人知识库的 AI 代理使用。它描述了使系统工作的模式、架构和操作规范。

将其作为技能或系统提示词放入您的代理工作区。您的代理会构建其余部分。

---

## 这是什么

一个个人智能系统，您的 AI 代理在此系统中构建并维护一个相互链接的 wiki，包含您对世界的所有认知 —— 人物、公司、交易、项目、会议、想法 —— 以结构化、交叉引用的 markdown 文件形式存在。代理负责编写和维护所有内容。您负责指导、策展和思考。

这是 Karpathy 的 LLM wiki 模式，但从研究笔记扩展到完整的运营知识库 —— 一个与您的日历、电子邮件、会议、社交媒体和联系人集成，保持持续更新的系统。

核心洞察：**知识管理 30 年来一直失败，因为维护工作落在人类身上。LLM 代理改变了这一格局 —— 它们不会感到无聊，不会忘记更新交叉引用，可以一次处理 50 个文件。** 您的 wiki 保持活力，因为维护成本几乎为零。

## 三个基本原则

### 1. 每条知识都有一个主要归属地（MECE 目录）

每条知识通过决策树，精确地归入一个目录。没有重复的页面，没有关于内容应该放在哪里的歧义。

这是最重要的结构决策。没有它，知识库会腐烂 —— 同一个事实存在于三个地方，有三个不同的版本，没有人知道哪个是最新的，代理（或人类）会停止信任系统。具有明确解析规则的 MECE 目录可以防止这种情况发生。

每个目录都有一个 `README.md`（解析器），回答两个问题：
1. **什么放在这里** —— 带有具体测试的正面定义
2. **什么不放在这里** —— 与相邻目录的关键区别，代理可能会混淆

大脑还有一个顶层的 `RESOLVER.md` —— 代理在归档任何内容时遵循的编号决策树。当两个目录似乎都合适时，消歧规则会打破僵局。当没有合适的目录时，项目会放入 `inbox/` —— 这本身就是一个信号，表明架构需要演进。

**代理在创建任何新页面之前必须读取解析器。这不是可选的。**

**重要细微差别：MECE 适用于目录，而不是现实。** 真实的人和实体是多面的 —— 一位政治创始人也可以是朋友、捐赠者、媒体人物和招聘候选人。解析器为他们的页面选择 *主要归属地*（people/），但页面本身使用类型化反向链接和交叉引用来展现他们的所有方面。MECE 规则防止重复页面，而不是重复关系。交叉引用是在不破坏"每个实体一个页面"规则的情况下保留邻接关系的方式。

### 2. 编译真相 + 时间线（双层页面）

每个大脑页面都有两层，用水平线分隔（`---`）：

**线上方 — 编译真相。** 始终最新，收到新信息时始终重写。以一段执行摘要开头。如果您只阅读这部分，您就知道当前状态。随后是结构化的 State 字段、Open Threads（活动项目 —— 解决后删除）和 See Also（交叉链接）。

**线下方 — 时间线。** 仅追加，从不重写。按时间倒序排列的证据日志。每个条目：日期、来源、发生了什么。当一个开放线程得到解决时，它会带着解决方案移动到这里。

如果有人问"当前状态是什么？" —— 阅读线上方。如果有人问"发生了什么？" —— 阅读线下方。顶部是当前摘要。底部是来源日志。

这是 Karpathy wiki 模式的杀手级功能：**综合是预先计算的。** 与 RAG 不同（LLM 在每次查询时从头重新推导知识），您的大脑已经完成了这项工作。交叉引用已经存在。矛盾已经被标记出来。

### 3. 丰富管道在每个信号上触发

每次任何信号触及一个人或公司 —— 会议、电子邮件、推文、日历事件、联系人同步、对话提及 —— 丰富管道就会触发。大脑作为正常操作的副作用而增长，而不是作为一项您需要记住去做的单独任务。

这是运营大脑与 Karpathy 研究 wiki 的区别。他描述了摄取您手动添加的来源。运营大脑更进一步 —— 每个管道（会议、电子邮件、社交媒体、联系人）在接触到的每个实体上自动触发丰富。您永远不必记得更新某人的页面。系统会自动完成，因为管道连接正确。

## 将其连接到您的代理

大脑必须作为硬规则（而不是建议）在代理的配置（AGENTS.md 或等效文件）中引用。具体来说：

1. **创建任何大脑页面之前 → 读取 RESOLVER.md。** 这应该在您的代理操作规则中，而不是埋在文档中。
2. **回答任何关于人物、公司、交易或战略的问题之前 → 首先搜索大脑。** 即使代理认为它知道答案。文件内容是最新的；代理对它们的记忆会过时。
3. **丰富技能在每个信号上触发。** 每个摄取途径 —— 会议处理、电子邮件分类、社交监控、联系人同步 —— 在遇到人或公司时都应调用丰富管道。这是硬连接，不是纪律问题。如果它依赖于代理的记忆，最终会被遗忘。
4. **修正是最高价值的数据。** 如果用户纠正了代理关于人、公司、交易或决策的信息 —— 立即写入大脑。不要批处理，不要延迟。

权威链：**代理配置（AGENTS.md）说"读取 RESOLVER.md" → RESOLVER.md 是决策树 → 每个目录的 README.md 是本地解析器 → schema.md 定义页面结构 → 丰富技能定义丰富协议。**

## 架构

三层：

**原始来源** —— 会议记录、电子邮件、推文、网络研究、API 响应、日历事件、联系人数据。不可变。代理从中读取但从不修改。存储在 `sources/` 和 `.raw/` 侧车目录中。

**大脑** —— 一个相互链接的 markdown 文件目录。人物页面、公司页面、交易页面、会议页面、项目页面、概念页面。代理完全拥有这一层。它创建页面，在新信息到达时更新它们，维护交叉引用，并保持一切一致。您阅读它；代理写入它。

**架构** —— 一份文档（本文件，加上 `schema.md` 和 `RESOLVER.md`），告诉代理大脑如何结构化、约定是什么以及遵循什么工作流。这是关键配置文件 —— 它使您的代理成为纪律严明的知识维护者，而不是通用聊天机器人。

## 数据库 + Markdown 架构

markdown wiki 是面向人类的层 —— 人类和 LLM 的主要接口。但它不是唯一的真相来源。结构化数据库层提供基础，markdown 从中生成。

### 四个数据库原语

**实体注册表** —— 规范 ID、所有别名、所有外部 ID（LinkedIn 成员 ID、X 用户 ID、电子邮件地址、电话号码）都在一个表中。这是"这是同一个人吗？"的单一真相来源。当您合并两个实体时，这是一个数据库操作（将两个 ID 指向同一个规范记录），而不是带有交叉引用修正的文件合并操作。

**事件分类账** —— 每个触及大脑的信号都是一个不可变事件：参加会议、收到电子邮件、发布推文、完成丰富、应用用户修正。事件具有来源：源、时间戳、置信度、原始负载引用。markdown 页面的时间线部分从此分类账生成。您永远不会因为页面重写出错而丢失事件。

**事实存储** —— 具有来源的结构化声明。"Jane Doe 是 Acme 的 CTO"，带有 `source=crustdata, confidence=high, observed_at=2026-04-07`。当两个来源不一致时（LinkedIn 说是 CTO，公司网站说是 VP Engineering），冲突表现为同一字段具有不同值的两个事实。线上方的编译真相部分从事实存储的最新置信值生成。矛盾成为数据，而不是错误。

**关系图** —— 实体之间的类型化边。Person→Company（角色：CTO，开始时间：2024-01），Person→Person（关系：共同创立公司），Company→Deal（类型：A 轮，日期：2025-03）。支持 markdown grep 无法回答的图查询："我认识谁投资了 AI 基础设施公司？"变成遍历，而不是祈祷。

### 为什么这很重要

- **身份解析** 成为数据库操作（合并实体 ID），而不是带有手动交叉引用修正的文件合并操作
- **矛盾是结构化的**（同一字段具有不同值和不同来源的两个事实），而不是文本化的（希望 LLM 注意到散文中隐藏的差异）
- **并发性解决** —— 事件追加到分类账，事实 upsert 到存储，markdown 重建。共享文件上不再有合并冲突
- **图查询有效** —— "我在这家公司认识谁？"和"这位投资者支持了哪些我也认识创始人的公司？"变成数据库查询，而不是不可能的 grep 链

### 文件层约定

markdown 层使用直接映射到数据库原语的约定：

1. **对结构化元数据使用 frontmatter** —— 任何您想要查询的内容（角色、公司、阶段、分数、标签）都放在 YAML frontmatter 中，而不是埋在散文中。这些映射到事实存储。
2. **对来源使用 `.raw/`** —— 保存每个带有来源和时间戳的 API 响应。这些映射到事实存储中的来源记录。
3. **将时间线视为事件流** —— 带日期、来源、仅追加。这些映射到事件分类账。
4. **保持编译真相与证据在概念上分离** —— 线上方是综合；线下方是证据。综合是生成的视图；证据是可查询的记录。
5. **一致使用规范 slug** —— 每个交叉引用使用文件名 slug。这些是注册表中的实体 ID。

## 实体身份和去重

在一个由会议、电子邮件、社交媒体、联系人及 API 提供数据的系统中，**实体身份是第一个真正的失败模式。** 没有规范身份层，您最终会得到微妙的分裂大脑页面 —— 会议记录中的"Jane Smith"、电子邮件中的"J. Smith"和 Twitter 中的"jsmith"都为同一个人生成单独的页面。

### 规范 slug

每个实体获得一个规范 slug，作为其稳定 ID：
- 人物：`first-last.md`（全小写，空格用连字符）
- 公司：`company-name.md`
- 如果出现冲突，消歧：`david-liu-crustdata.md`、`david-liu-meta.md`

文件名就是身份。所有引用、交叉引用和 .raw/ 侧车都使用此 slug。

### 别名

人们在不同来源有许多名字。frontmatter 的 `aliases` 字段捕获所有已知变体：

```yaml
aliases: ["Jenny Shao", "Jenny G. Shao", "JennyGShao", "jennifer.shao@company.com"]
```

别名包括：会议记录中的拼写错误、娘家姓、昵称、电子邮件地址、社交用户名和语音变体。当丰富技能遇到已知实体的新名称变体时，它会将变体添加到别名中 —— 不会创建新页面。

### 去重协议

创建任何新页面之前，代理必须：
1. 按名称搜索现有页面（精确和模糊）
2. 搜索所有页面的别名：`grep -rl "NAME_VARIANT" /data/brain/people/ --include="*.md"`
3. 检查 .raw/ 侧车中是否有匹配的电子邮件地址或社交用户名
4. 如果找到匹配 → 更新现有页面（如果名称变体是新的，添加别名）
5. 如果没有匹配 → 创建新页面

### 合并协议

当您发现两个页面是同一个人时：
1. 选择更完整的页面作为保留页
2. 将所有时间线条目从重复页合并到保留页（按时间顺序）
3. 合并所有别名
4. 更新所有指向重复页的交叉引用
5. 删除重复页
6. 提交消息：`merge: [duplicate] into [survivor]`

在每周的 lint 期间，积极寻找潜在的重复项：相似的名字、相同的公司、不同页面上的相同电子邮件。

## 关键消歧规则

最常见的归档混淆及其解决方法：

- **概念 vs. 想法：** 您能将其作为框架 *教授* 吗？→ 概念。您能 *构建* 它吗？→ 想法。
- **概念 vs. 个人：** 您会在专业演讲中分享它吗？→ 概念。它是私人反思吗？→ 个人。
- **想法 vs. 项目：** 有人在研究它吗？是 → 项目。否 → 想法。毕业时刻是工作开始时。
- **写作 vs. 媒体：** 写作是 *作品*（随笔）。媒体是 *生产和分发基础设施*（内容管道、社交监控）。
- **写作 vs. 概念：** 概念页面是提炼的（200 字编译真相）。随笔是展开的散文（论点、叙事、故事）。
- **人物 vs. 公司：** 是关于 *他们作为人* 吗？→ people/。是关于 *组织* 吗？→ companies/。两个页面相互链接。
- **家庭 vs. 个人：** PA 会执行它吗？→ household（运营）。是私人反思吗？→ personal。
- **来源 vs. .raw/ 侧车：** 每个实体的丰富数据 → .raw/ 侧车。批量多实体导入 → sources/。

当没有合适的目录时，归档到 inbox/ 并标记它。这是架构需要演进的信号。

## 页面类型和模板

### 人物

最重要的页面类型。一个好的人物页面是一份研究充分的简报 —— 而不是 LinkedIn 抓取。

```markdown
# Person Name

> 执行摘要：他们是谁，为什么重要，与他们进行任何互动时您应该知道什么。

## State
- **Role:** 当前职位
- **Company:** 当前组织
- **Relationship:** 与您的关系（朋友、同事、投资者等）
- **Key context:** 当前最重要的 2-4 个要点

## What They Believe
世界观、立场、基本原则。他们坚守的立场。
每个声明必须引用其来源和类型：
- [信念] — observed: [推文/会议/文章, 日期]
- [信念] — self-described: [采访/传记, 日期]
- [信念] — inferred: [N 次互动中的模式, confidence: high/medium/low]

## What They're Building
当前项目、最近发布的产品、产品方向。

## What Motivates Them
抱负驱动因素、职业轨迹、是什么让他们起床。
区分他们说的激励因素（self-described）和他们的行为暗示的因素（observed/inferred）。

## Communication Style
他们更喜欢如何沟通。他们如何处理分歧。
什么能让他们在对话中充满活力。
这部分价值很高，但需要仔细的来源。
规则：仅根据直接观察（会议行为、电子邮件/推文中的语言、可见模式）在此处写作。永远不要从单个数据点概括。标记置信度级别。

## Hobby Horses
他们反复沉迷的话题。他们公开声音中的 recurring themes。

## Assessment
- **Strengths:** 他们擅长什么。具体说明。
- **Gaps:** 他们可以成长的地方。具体说明且公平。
- **Net read:** 一行综合。
- **Confidence:** high（5+ 次互动）/ medium（2-4 次）/ low（1 次或推断）
- **Last assessed:** YYYY-MM-DD

## Trajectory
上升、平稳、转型、下降？证据。

## Relationship
互动历史、温度、动态。

## Contact
- Email, phone, LinkedIn, X handle, location

## Network
- **Close to:** 经常一起出现的人
- **Crew:** 他们属于哪个集群

## Open Threads
- 活动项目、待处理的介绍、跟进事项

---

## Timeline
- **YYYY-MM-DD** | Source — What happened.
```

所有部分都是可选的 —— 包含您拥有的内容，将空部分保留为 `[No data yet]` 而不是省略。**结构本身就是未来丰富的提示。** 当一个部分显示 `[No data yet]` 时，代理知道下次遇到此人时要寻找什么。

原则：事实是基本要求。背景是价值所在。

### 人物页面的认知规范

背景部分（信念、动机、沟通风格、评估）是系统中价值最高的部分，但也最容易产生幻觉。代理可能从稀疏证据中过度概括或过度拟合最近的一次互动。规则：

- **每个声明引用其来源。** 不是"她很激进"而是"她在 3 月 15 日的会议上强烈反对定价（observed）。"
- **三种来源类型：** `observed`（您看到发生的）、`self-described`（他们自己说的）、`inferred`（您在字里行间读到的）。每个都标记。
- **置信度跟踪互动次数。** 一次会议 = 低置信度。五次会议 = 高置信度。不要从稀疏数据中写出确定性评估。
- **时效性很重要。** 2 年前的信念可能不再适用。标记日期。
- **永远不要从单个数据点概括。** "她在一次会议中似乎很沮丧"是时间线条目。模式需要多个观察。
- **用户的修正覆盖一切。** 如果用户说"关于她的那是错的"，立即更新 —— 该修正是系统中最高置信度的信号。

## 丰富管道

**这是最重要的操作模式。** 每次您的代理遇到一个人或公司 —— 在会议、电子邮件、推文、日历事件、联系人同步中 —— 它应该丰富相应的大脑页面。

丰富不仅仅是"查找他们的 LinkedIn"。它是：

- **他们相信什么** — 立场、世界观、公开姿态
- **他们正在构建什么** — 当前项目、正在发布的内容
- **什么激励他们** — 抱负、职业轨迹
- **他们的沟通风格** — 他们如何参与、什么能激发他们
- **他们与您的关系** — 历史、背景、开放线程
- **硬事实** — 角色、公司、联系方式、融资（基本要求）

事实是基本要求。背景是价值所在。

### 何时丰富

**任何时候** 出现人或公司信号：
- 有人在会议记录中被提及 → 丰富
- 有人给您发电子邮件 → 丰富
- 有人在社交媒体上与您互动 → 丰富
- 出现新联系人 → 丰富
- 您在对话中提到某人，而他们的页面很薄 → 丰富
- 公司宣布融资、发布产品、成为新闻 → 丰富

### 丰富来源（按价值排序）

1. **您自己的互动** — 您关于他们说的话，他们对您说的话（最高信号）
2. **会议记录** — 最丰富的背景来源
3. **电子邮件线程** — 语气、紧迫性、关系动态
4. **社交媒体** — 信念、公开定位、他们参与的人
5. **网络搜索** — 背景、媒体报道、演讲
6. **人物 API** — 结构化个人资料数据（职业历史、教育、技能、联系方式）
7. **公司 API** — 融资、投资者、估值、人数、财务
8. **联系人数据** — 电子邮件、电话、位置

### 数据源技能

每个外部数据源应该是自己命名的技能，包含完整的 API 文档、认证模式和使用说明。丰富技能编排它们 —— 它根据层级决定 *调用哪些* 来源，然后委托给单个技能处理 *如何* 调用 API。

这保持了 DRY：丰富技能拥有逻辑（何时丰富、什么层级、提取什么），每个数据源技能拥有 API 契约（端点、认证、速率限制、陷阱、验证规则）。

推荐的数据源技能：

- **网络搜索** — 广泛的关键词搜索（Brave、Google 等）。快速背景、媒体报道、融资。
- **语义搜索** — 比关键词搜索更适合查找特定人物、LinkedIn URL、个人写作。（Exa、Perplexity 等）
- **社交搜索** — X/Twitter、Bluesky 等用于公开声音：信念、项目、参与模式。
- **人物丰富** — 结构化 LinkedIn 式数据：职业历史、教育、技能、联系方式。（Crustdata、Proxycurl、People Data Labs 等）
- **网络搜索** — 搜索您的专业网络以寻找温暖的介绍和联系。（Happenstance、Clay 等）
- **公司情报** — Pitchbook 级数据：融资轮次、投资者、估值、人数、财务。（Captain API、Crunchbase 等）
- **会议历史** — 搜索过去的会议以查找与此实体的互动。（Circleback、Otter、Fireflies 等）
- **联系人数据** — 来自您联系人的电子邮件、电话、位置。（Google Contacts 等）

新人物的典型丰富流程：
1. **网络搜索** → 找到 LinkedIn URL、职业轨迹、备用名称
2. **人物丰富** → 深度结构化数据（技能、工作历史、教育、联系方式）
3. **语义搜索** → 找到个人网站、演讲、揭示信念和观点的写作
4. **社交搜索** → 他们的公开声音、他们参与的人、爱好话题
5. **网络搜索** → 媒体报道、最近新闻、演讲
6. **会议历史** → 过去与您的互动

新公司的典型丰富流程：
1. **公司情报** → 融资、投资者、人数、财务
2. **网络搜索** → 产品、媒体报道、吸引力
3. **社交搜索** → 公司的公开定位
4. **人物丰富** → 丰富创始人/关键团队成员（每个人触发人物丰富）

### 丰富层级（不要过度丰富）

- **Tier 1（关键人物）：** 完整管道 —— 所有来源。核心圈子、商业伙伴、重要合作者。
- **Tier 2（知名人物）：** 网络搜索 + 社交 + 大脑交叉引用。您偶尔互动的人。
- **Tier 3（次要提及）：** 仅从来源提取信号，追加到时间线。其他值得跟踪的所有人。

一个包含真实互动数据的薄页面比一个塞满通用网络结果的胖页面更好。不要在没有公开存在的人身上浪费 10 次 API 调用。

### 原始数据侧车

每个丰富 API 响应保存为 JSON 侧车：

```
people/jane-doe.md              ← brain page (curated, readable)
people/.raw/jane-doe.json       ← raw API responses
```

JSON 按来源键控，带有获取时间戳：

```json
{
  "sources": {
    "crustdata": { "fetched_at": "2026-04-05T...", "data": { ... } },
    "web_search": { "fetched_at": "...", "data": { ... } }
  }
}
```

大脑页面是提炼版本。原始数据是存档。

放入大脑页面（提炼）的内容：位置、当前职位、公司、标题、教育（一行）、职业轨迹（浓缩）、顶级技能、社交用户名、个人资料图片永久链接。

仅保留在 .raw/ 中的内容：完整工作历史（包含职位描述）、完整技能列表、每个雇主的公司描述、平台特定 ID、关注者/连接数、完整 API 响应体。

重新丰富时：用新数据 + 新时间戳覆盖源键。不要追加 —— 替换。

### 验证规则

从人物/公司 API 自动丰富时：
- **低连接/关注者数量（例如 <20）：** 可能是错误的人。保存到 .raw/，带有 `"validation": "low_connections"` 标志。不要自动写入大脑页面。
- **名称不匹配：** 如果返回的名称与实体不共享姓氏，跳过。
- **明显是玩笑的个人资料：** 职业轨迹提到荒谬头衔 —— 跳过。
- **有疑问时：** 保存原始数据但不更新大脑页面。错误数据比没有数据更糟。

### 浏览器预算

如果丰富涉及基于浏览器的查找（LinkedIn、认证页面），设置每日预算（例如每天 20 次查找）以避免账户被标记。对于批量工作，首选基于 API 的丰富服务 —— 它们不触及用户的浏览器会话。

## 条目标准 — 谁获得页面

不是每个人都值得一个大脑页面。根据关系重要性调整页面创建规模：

**始终创建页面：**
- 任何您进行过一对一或小团体会议的人
- 关键同事、合作伙伴和直接合作者
- 任何有良好工作关系或更好关系的人
- 家人、亲密朋友、核心圈子

**如果存在信号则创建：**
- 联系人中有最近互动的人
- 在对话中被提及且有背景的任何人
- 有多个共享事件的活动联系人

**不要创建：**
- 来自大规模活动嘉宾名单的随机名字，没有互动
- 没有识别背景的单名条目
- 完全没有关系信号的联系人

有疑问时：用户从这个条目中受益吗？如果没有，跳过。

## 技能架构

技能是系统的模块化构建块。有三种类型，理解它们如何组合至关重要。

### 1. 数据源技能（叶节点）

每个外部 API 或数据源都有自己命名的技能。技能拥有 API 契约：端点、认证、速率限制、错误处理、验证规则和响应的样子。

示例：
- **人物丰富**（Crustdata、Proxycurl、People Data Labs）—— 结构化 LinkedIn 式数据
- **网络搜索**（Happenstance、Clay）—— 搜索专业网络，找到共同联系人
- **公司情报**（Captain API/Pitchbook、Crunchbase）—— 融资、投资者、财务
- **语义搜索**（Exa、Perplexity）—— 找到 LinkedIn URL、个人网站、写作
- **会议历史**（Circleback、Otter、Fireflies）—— 过去的会议记录和笔记
- **日历/联系人**（Google Calendar、Google Contacts 通过集成工具）—— 日程、联系方式
- **社交媒体**（X API、Bluesky API）—— 公开帖子、参与度、关注者数据
- **工作区工具**（Gmail、Slack、Drive 通过集成工具）—— 电子邮件线程、消息、文档

数据源技能 **从不** 由用户直接调用。它们由编排技能调用（如下）。

### 2. 编排技能（协调器）

这些技能包含 *逻辑* —— 它们决定做什么，然后委托给数据源技能处理怎么做。

**丰富技能** 是最重要的编排技能。它决定：
- 这是 CREATE（新页面）还是 UPDATE（新信号）？
- 这个实体是什么层级？（决定调用哪些数据源）
- 从源材料中提取什么信号类型？
- 按什么顺序调用哪些数据源技能？
- 如何将结果写入大脑？

其他编排技能：
- **会议摄取** — 从会议工具中提取会议，创建大脑会议页面并进行分析，然后为每个与会者和讨论的公司调用丰富
- **电子邮件分类 / 执行助理** — 处理收件箱，处理日程安排，然后在遇到人或公司时调用丰富
- **社交监控** — 扫描公共社交媒体以查找提及和参与，然后为知名账户调用丰富

### 3. 管道技能（端到端工作流）

这些是面向用户的技能，将多个编排和数据源技能链接在一起：
- **晨间简报** — 读取日历 + 任务 + 大脑状态 + 最近信号 → 生成简报
- **人物研究** — 给定一个名字，运行完整的 Tier 1 丰富并呈现结果
- **每周大脑维护** — 运行 lint，标记过期页面，建议丰富目标

### 它们如何组合

```
User says "tell me about Jane Doe"
  → Agent searches brain (grep/index)
  → Page is thin → calls enrich skill (orchestration)
    → enrich determines Tier 1
    → calls happenstance skill (data source) → gets LinkedIn URL
    → calls crustdata skill (data source) → gets full profile
    → calls exa skill (data source) → finds personal writing
    → calls web_search (built-in tool) → gets press coverage
    → calls meeting history (data source) → finds past meetings
    → writes brain page, saves .raw/ sidecar, cross-references
  → Agent presents the enriched page to user
```

```
Cron fires "meeting ingestion" every afternoon
  → meeting-ingestion skill (orchestration) pulls new meetings
  → for each meeting: creates brain meeting page
  → for each attendee: calls enrich skill (orchestration)
    → enrich calls relevant data source skills based on tier
  → for each company discussed: calls enrich skill
  → extracts tasks, commits brain repo
```

核心洞察：**数据源技能是无状态且可重用的。** 无论触发器是会议、电子邮件、社交提及还是直接用户请求，丰富技能都可以调用 Crustdata。数据源技能不关心请求来自哪里。

## 丰富如何连接到一切

丰富技能是中心枢纽。每个摄取途径都汇聚到它：

```
Meeting ingestion ───────┬─────────────────────────┬─── people enrichment API
Email triage ────────────┤                         ├─── company intelligence API
Social monitoring ───────┤    ENRICH SKILL         ├─── network search API
Contact sync ────────────┤   (orchestration)       ├─── semantic search API
Manual conversation ─────┤                         ├─── social search API
Calendar events ─────────┤                         ├─── web search
Webhooks ────────────────┴─────────────────────────┴─── meeting history API
                              │
                              ▼
                         BRAIN REPO
                    (people/, companies/,
                     meetings/, deals/)
```

进入丰富技能的每个箭头都带有一个 **信号**（来自源的原始信息）和一个 **实体**（要丰富的人或公司）。丰富技能：

1. **检查大脑状态** — 页面存在吗？它薄吗？
2. **确定层级** — Tier 1（完整管道）、Tier 2（网络 + 社交 + 交叉引用）、Tier 3（仅源提取）
3. **从源材料中提取信号**（信念、动机、轨迹、事实）
4. **根据层级调用数据源技能**（每个技能都是命名的、文档化的模块）
5. **写入大脑** — CREATE（通过 RESOLVER.md）或 UPDATE（追加时间线、更新编译真相）
6. **交叉引用** — 更新所有链接的实体页面
7. **保存原始数据** 到 `.raw/` 侧车
8. **提交** 到大脑仓库

关键连接规则：**每个摄取技能必须调用丰富。** 这不是可选的或理想的。这是结构性的。如果添加了新的摄取途径（例如 Slack 监控技能），其实现必须包含"对于提到的每个人/公司，调用丰富技能。"如果缺少这一行，大脑将停止从该来源复合。

## 自动化 Cron 作业

大脑不仅仅在您积极使用时增长。Cron 作业使系统自主 —— 即使您在睡觉，大脑也会被维护，收件箱会被分类，会议会被摄取，提及会被监控。

### Cron 架构

Cron 作业作为 **孤立的代理会话** 运行 —— 它们有自己的上下文，读取自己的技能，不阻塞主对话线程。它们可以发布到特定的通知频道（Telegram 主题、Slack 频道、Discord 线程）或静默工作。

每个 cron 作业本质上是："醒来，读取技能，做工作，发布结果（如果什么都没发生则保持沉默），回去睡觉。"

### 推荐的大脑驱动系统的 cron 作业

**高频率（每 10-30 分钟）：**
- **电子邮件监控** — 扫描收件箱，按优先级分类，向通知频道发布摘要。直接处理低风险项目（日程安排、确认）。
- **消息监控** — 检查关键沟通渠道中来自重要联系人的未回复消息。提供建议的回复。

**中等频率（每 1-3 小时）：**
- **社交雷达** — 扫描公共社交媒体以查找对您或您组织的提及、参与、新兴叙事。提醒需要关注的项目。为与您互动的知名新账户调用丰富。
- **心跳** — 综合检查。日历前瞻、任务回顾、电子邮件扫描、大脑状态审查。如果需要关注则发布；否则保持沉默。

**每日：**
- **晨间简报** — 日历 + 任务 + 紧急项目 + 夜间信号 → 一条通知。"这是您的一天"消息。
- **任务准备** — 归档昨天完成的任务，从日历 + 待办事项 + 重复项目构建今天的列表。
- **会议摄取** — 从您的会议工具中提取所有新会议，运行完整摄取（创建会议页面，传播到实体页面，提取任务）。这是最重的 cron 作业 —— 它触及最多的大脑页面。
- **社交媒体收集** — 归档您自己的帖子，跟踪参与速度，检测删除。输入到 media/ 页面。

**每周：**
- **大脑 lint** — 运行完整的维护过程：矛盾、过期页面、孤立页面、缺失交叉引用、MECE 归档违规。发布报告。
- **丰富扫描** — 找到 90+ 天未丰富的大脑页面，或有许多 `[No data yet]` 部分的页面。将它们排队重新丰富。
- **联系人同步** — 从您的联系人中提取最近添加的内容，与大脑交叉引用。为重要的新联系人创建页面。

### Cron 如何为大脑提供数据

核心洞察：**cron 作业是自主的丰富引擎。** 没有它们，大脑只在您积极与代理交谈时增长。有了它们：

- 电子邮件监控遇到一个人 → 调用丰富 → 大脑增长
- 会议摄取处理记录 → 为每个与会者调用丰富 → 大脑增长
- 社交雷达检测到一个新的知名账户 → 调用丰富 → 大脑增长
- 联系人同步找到一个新联系人 → 调用丰富 → 大脑增长
- 丰富扫描找到过期页面 → 用新数据调用丰富 → 大脑保持最新

大脑全天候复合，因为 cron 作业被连接到调用丰富。用户睡觉；大脑不睡觉。

### Cron 作业设计规则

1. **无事发生时保持沉默。** 如果 cron 没有找到任何新东西，它应该不产生任何输出。没有"没有报告"消息。这至关重要 —— 嘈杂的 cron 会被禁用。
2. **发布到特定频道。** 每个 cron 发布到其指定的通知频道（例如，电子邮件 cron → Emails 主题，社交雷达 → Social Alerts 主题）。不要混合信号。
3. **为繁重工作生成子代理。** cron 会话应该保持轻量级。如果会议摄取需要处理 5 个会议并更新 30 个实体页面，则为实体传播生成子代理。
4. **幂等性和检查点感知。** 每个 cron 应该跟踪它已经处理的内容（在状态文件中，如 `meeting-notes-state.json`），这样它就不会在下一次运行时重做工作。
5. **尊重安静时间。** 除非真正紧急，否则不要在晚上 11 点到早上 7 点之间发布。cron 应该在发布前检查时间。
6. **每个摄取 cron 必须调用丰富。** 这是结构规则。处理会议但不丰富与会者的 cron 是错误，不是功能。

### 示例：一切如何组合在一起

自主大脑系统中的一个典型下午：

1. **下午 3:00** — 电子邮件监控 cron 触发。扫描收件箱。找到 3 封新邮件：日程安排请求、融资公告和创始人寻求建议。
   - 直接处理日程安排请求（检查日历，回复可用时间）
   - 调用丰富处理融资公告中的公司 → 用新一轮更新公司页面
   - 将创始人的电子邮件发布到通知频道供用户处理

2. **下午 3:15** — 会议摄取 cron 触发。找到今天的 2 个新会议。
   - 创建 2 个大脑会议页面并进行分析
   - 为两个会议的 8 名与会者调用丰富 → 更新 8 个人物页面
   - 为讨论的 3 家公司调用丰富 → 更新 3 个公司页面
   - 提取 4 个行动项 → 添加到任务列表

3. **下午 3:30** — 社交雷达 cron 触发。检测到一名记者正在写关于用户组织的帖子。
   - 向 Social Alerts 频道发布警报
   - 调用丰富处理记者 → 创建/更新他们的人物页面，包含最近活动

4. **下午 4:00** — 心跳触发。日历显示 1 小时后有会议。与会者的大脑页面上次丰富是在 3 个月前。
   - 触发对与会者的新丰富传递
   - 发布准备笔记："1 小时后与 X 会面。自上次会面以来发生了以下变化。"

用户没有要求任何这些。大脑增长了 12 个页面，用户完全准备好参加下午 4:00 的会议 —— 因为管道连接正确。

## 生产系统的工作示例

这些示例展示了架构如何端到端运行。名称和细节是通用的，但技能链是精确的 —— 每个技能调用、每个文件写入、每个 cron 触发器都是实际工作方式。

### 示例 1：会议摄取 — 完整链

Cron 作业在下午 3:00 每日触发，提示："读取 skills/meeting-ingestion/SKILL.md 并处理今天的会议。"

**步骤 1：技能链加载。** 会议摄取技能的序言说"读取 skills/enrich/SKILL.md" — 因此代理在接触任何数据之前加载丰富协议。这至关重要：这意味着代理知道如何处理遇到的每个人和公司。

**步骤 2：提取新会议。** 代理调用会议历史数据源技能（在此系统中是 Circleback）。它检查状态文件（`memory/meeting-notes-state.json`），该文件跟踪上次处理的会议 ID。找到自上次运行以来的 2 个新会议。

**步骤 3：处理会议 1 — "产品评审与 Sarah Chen 和 Mike Torres。"**

代理创建 `brain/meetings/2026-04-07-product-review.md`，包含：
- 线上方自己的分析（不是 AI 摘要的副本 —— 通过大脑已有的关于与会者和项目的知识重新构建）
- 关键决策、行动项和与其他大脑页面的连接
- 线下方完整记录

**步骤 4：丰富与会者。**

对于 **Sarah Chen** — 代理搜索大脑：`grep -rl "Sarah Chen" /data/brain/people/`。找到 `people/sarah-chen.md`。读取它。页面上次丰富是在 2 周前，覆盖范围良好。→ **Tier 3**：仅从本次会议提取信号。追加到她的时间线："2026-04-07 | Meeting — Pushed back on timeline for launch, wants more QA. Concerned about API stability." 更新她的 Open Threads 与新的跟进项目。

对于 **Mike Torres** — 大脑搜索找到 `people/mike-torres.md`。页面存在但很薄：只有一个名字、头衔和一个以前的会议条目。→ **Tier 2**：网络搜索 + 社交 + 大脑交叉引用。代理找到他最近的博客文章（输入到 What They Believe）、他的 X 活动（输入到 Hobby Horses），并将他与其他两个提到他的大脑页面交叉引用。更新线上方的编译真相。

对于 **"Alex from Meridian Labs"**（在会议中提及但不是与会者）— 大脑搜索找不到。→ **CREATE 路径**：
1. 读取 RESOLVER.md："a specific named person" → `people/`
2. 使用 schema.md 中的人物模板创建 `people/alex-rivera.md`
3. 运行 **Tier 1 丰富**（完整管道）：网络搜索 → 找到 LinkedIn URL。人物丰富 API → 完整结构化个人资料。语义搜索 → 找到会议演讲。网络搜索 → 找到 Meridian Labs 最近融资的媒体报道。
4. 将原始 API 响应保存到 `people/.raw/alex-rivera.json`
5. 交叉引用：更新 `companies/meridian-labs.md` 链接到 Alex 的页面

**步骤 5：丰富讨论的公司。** Meridian Labs 被广泛讨论。代理检查 `companies/meridian-labs.md` — 存在但融资数据是 4 个月前的。调用公司情报 API → 获取新一轮数据。更新页面。

**步骤 6：提取行动项。** 在记录中找到 3 个行动项 → 追加到 `ops/tasks.md`。

**步骤 7：对会议 2 重复。** 相同流程。

**步骤 8：提交并通知。**
```bash
cd /data/brain && git add -A && git commit -m "meetings: 2026-04-07 product review, investor sync" && git push
```
向 Meetings 通知频道发布摘要："处理了 2 个会议。创建了 1 个新人物页面（Alex Rivera）。更新了 4 个实体页面。提取了 5 个行动项。"

### 示例 2：电子邮件分类 — 解析器 + 丰富在行动中

电子邮件监控 cron 在中午 12:00 触发。提示："读取 skills/executive-assistant/SKILL.md 和 skills/gmail/SKILL.md。分类收件箱。"

**步骤 1：提取收件箱。** 代理通过其工作区集成调用 Gmail 数据源技能。自上次检查以来收到 8 封新邮件。

**步骤 2：分类和处理。** 大多数电子邮件是常规的：2 个日程安排确认（直接处理 —— 检查日历，发送确认）、3 个新闻通讯（归档）、1 个内部 FYI（记录）。但有一封脱颖而出：

**来自"David Park, GP at Ridgeline Ventures"的电子邮件** — 主题："NovaTech 的 A 轮 — 共同投资机会。"代理从未见过这个人。

**步骤 3：丰富未知发件人。**

代理调用丰富技能。丰富搜索大脑：
```bash
grep -rl "David Park" /data/brain/people/ --include="*.md"  # no results
grep -rl "Ridgeline" /data/brain/companies/ --include="*.md"  # no results
grep -rl "david.park@ridgeline" /data/brain/people/ --include="*.md"  # no results (alias search)
```

没有匹配。→ **CREATE 路径。**

1. 读取 RESOLVER.md："a specific named person" → `people/`
2. 运行 **Tier 2 丰富**（这是一封主动发来的电子邮件，还不是关键关系）：
   - 网络搜索：在 Ridgeline 的网站上找到 David Park 的个人资料。GP，专注于企业 SaaS。之前在另外两家基金工作。
   - 社交搜索：找到他的 X 账户。最近关于 AI 基础设施、开发者工具的帖子。上周转发了一篇关于 NovaTech 的文章。
   - 大脑交叉引用：搜索 NovaTech → 找到 `companies/novatech.md` 存在（来自 2 个月前的会议）。交叉链接。
3. 创建 `people/david-park.md`，包含找到的内容 — 角色、基金、投资重点、公开声音、与 NovaTech 的联系。
4. 还检查 `companies/ridgeline-ventures.md` — 不存在。使用从网络搜索中了解到的内容创建一个薄页面。

**步骤 4：回到 EA 技能。** 现在代理有了背景。它对电子邮件进行分类：
- 优先级：中等（共同投资机会，不紧急）
- 背景：David Park 是一家专注于企业 SaaS 的基金的 GP。NovaTech 已经在大脑中，来自之前的会议。
- 需要操作：用户应该审查

发布到电子邮件通知频道：
